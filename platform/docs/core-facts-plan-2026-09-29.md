# Core facts plan builder

`apps/api/src/composition/core-facts-plan.ts` is a pure plan builder for mounted Core synthetic scenarios. After reading the run's exact immutable resolved-profile snapshot, the host passes the builder its `CoreExampleScenario`, actual `runProfileRef`, `resolvedProfileHash`, the resolved snapshot's actual `mappingRefs`, the selected exact `definitionRef`, trusted `ScopeRef`, and question. The builder does not use a deployment's base profile/mapping set as a substitute for the run pins. It holds no run/profile service, database, model or host dependency.

The run profile id/version and resolved-profile hash come from the actual immutable run snapshot. The selected scenario is resolved from that snapshot's industry ref; its id need not match the run profile id, since a published profile may select a different mounted industry pack. The hash must be a SHA-256 digest; the selected definition ref must exactly equal the selected scenario's mounted schema ref; each resolved mapping id/version/digest and source object must belong to that scenario's physical mappings. Unmounted or mismatched pins are rejected with `CoreFactsPlanError` before any plan is produced. An empty resolved mapping set is permitted because published-facts lookup does not execute a physical mapping; the empty set remains part of the plan identity.

The accepted input is `facts:<attributeId>` or up to three comma-separated registered attribute IDs. Property identifiers are matched exactly against the selected schema, so uppercase, dots and non-ASCII identifiers remain valid when declared; they are bounded to 256 UTF-8 bytes each and 1,024 bytes for the whole shortcut. Empty/malformed items, duplicates, unknown attributes, IDs ambiguous across schema objects, and lists above three are rejected with `CoreFactsPlanError`. Each accepted property becomes an independent read-only `ontology_lookup` step with a safe ordinal step ID, using the same trusted scope and selected definition version. The deterministic `planRef` digest binds scope, actual run profile and resolved hash, exact definition and resolved mapping refs, selected properties and generated steps, so the same question under different run pins produces a different plan identity. The plan starts no loop and opens no budget; execution continues through the controller's shared run ledger.

Single-property questions preserve the existing `facts:x` UX and lookup shape. The plan module does not accept free-form natural language or invoke JEV/generation as a fallback. A host should translate `CoreFactsPlanError` to its existing structured capability/request error and must supply only the scenario resolved from the actual run snapshot.

The focused unit test loads the checked-in synthetic scenarios and exercises single- and three-property plans, uppercase/dotted/Unicode declared identifiers, active run profile IDs/versions different from deployment-base profiles, resolved snapshot hash and mapping-set identity, and malformed/unknown/duplicate/ambiguous/over-limit or unmounted pins. It uses no database or model and does not claim end-to-end host wiring.
