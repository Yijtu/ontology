# Electron 客户端 + 远程服务端（设计）

状态：设计已定，待实施。范围：通用 Core 与公共前端；不含具体行业/客户业务内容。

## 1. 目标

把现在的「本机开发环境」变成「一个服务端 + 一个桌面客户端」：

- 服务端：部署在一台机器/内网上，托管 API 与前端产物，被多个客户端访问。
- 客户端：Electron 应用，双击即用；用户只需填服务端地址并登录，不接触 Node、pnpm、Docker、PowerShell。

不改业务语义：所有对象、审核、发布、研究、证据与预算规则保持现状。

## 2. 现状与阻塞（已核对代码）

| 阻塞 | 事实 | 影响 |
|---|---|---|
| 只有回环开发身份 | `apps/api/src/core-main.ts` 的 `authenticateLocalRequest` 对非 loopback 直接返回 `undefined`；`resolveLocalDevPrincipal` 拒绝非 `development` 模式与非回环地址 | 任何远程客户端都必然 401，**没有登录体系** |
| 无静态托管 | `apps/web` 只由 Vite dev server 提供；API 未注册静态文件与 SPA fallback | 客户端没有可加载的 UI |
| 监听地址写死 | `app.listen({ host: '127.0.0.1', ... })` | 远程不可达 |
| 无 CORS 需求 | 若客户端加载服务端托管的 UI，则同源，不需要 CORS | 只有「客户端自带 UI」时才需要，本期不做 |

`RequestAuthenticator` 已是干净接缝：认证改造不需要触碰业务层。

## 3. 架构

```
┌──────────────────────────┐        HTTPS（反代终止）        ┌────────────────────────────┐
│ Electron 主进程           │  ───────────────────────────▶  │ 反向代理（Caddy/Nginx）      │
│  - 窗口/托盘/更新/钥匙串   │                                │  - TLS、压缩、超时、限流       │
│  - 保存服务端地址与令牌    │                                └──────────┬─────────────────┘
└──────────┬───────────────┘                                           │
           │ 加载（同源）                                                 ▼
           │                                              ┌────────────────────────────┐
           └────────────────────────────────────────────▶ │ Core API（Fastify）          │
                                                          │  - 认证中间件（令牌/OIDC）    │
                                                          │  - /api/* 业务路由           │
                                                          │  - /* 静态 UI + SPA fallback │
                                                          └──────────┬─────────────────┘
                                                                     ▼
                                                          PostgreSQL（控制库 + RLS）
                                                          对象存储（可换 S3 兼容）
```

关键决定：**渲染进程加载的是服务端托管的同一份 UI**，不是客户端内置的一套。这样 UI 随服务端升级，客户端只负责壳与凭据；也天然同源，不需要 CORS。

## 4. 服务端改造

1. **监听地址可配**：新增 `CORE_API_HOST`（默认 `127.0.0.1`，部署时显式设 `0.0.0.0`）。默认值不变，避免误把开发实例暴露到网络。
2. **托管前端产物**：`pnpm run build:web` 后，API 提供 `/*` 静态文件与 SPA fallback（非 `/api`、非 `/healthz` 的 GET 返回 `index.html`）。
   - 需要正确的 MIME、`Cache-Control`（带 hash 的资源长缓存，`index.html` 不缓存）。
   - 路径穿越必须拒绝。
3. **认证（分两步）**
   - **阶段 1（A1，部署级令牌）**：`CORE_API_TOKEN` 设了才启用。请求需带 `Authorization: Bearer <token>`；校验通过后用 `CORE_TENANT_ID` / `CORE_SPACE_ID` 与固定角色集（与本地开发一致：业务角色 + 可选 operator）构造 `Principal`。
     - 令牌比较必须常数时间；日志、错误、健康检查都不得回显令牌。
     - 设置令牌后**只接受令牌**：不再保留回环旁路，否则服务器本机上的任意进程无需令牌即可获得全部角色。`CORE_API_TOKEN` 未设时行为与现在完全一致（仅回环开发身份）。
   - **阶段 2（A2，OIDC）**：授权码 + PKCE，系统浏览器登录、回环回调换会话；主体映射到 `Principal`。多用户与按用户隔离在这一步解决。
4. **审计与限制**：认证失败返回稳定 `UNAUTHENTICATED`；记录主体与 traceId（不含令牌）；对认证失败做限流留给反代。
5. **CSP 与安全响应头**：为 Electron 渲染进程准备 `Content-Security-Policy`（`default-src 'self'`、禁止 `unsafe-eval`、仅允许必要的 `connect-src`）、`X-Content-Type-Options`、`Referrer-Policy`。
6. **健康与版本**：客户端启动先 `GET /healthz` 判可用，再用 `/api/v1/core/deployment` 做能力握手；不匹配时给出「客户端过旧/服务端过旧」，而不是白屏。

## 5. 客户端设计（Electron）

- **进程模型**：主进程负责窗口、托盘、协议、更新、凭据；渲染进程只加载远程 UI，开启 `contextIsolation`、`sandbox`，**禁用 `nodeIntegration`**，不注入任何 Node 能力。
- **凭据**：令牌存 OS 钥匙串（Electron `safeStorage`，Windows DPAPI）；渲染进程拿不到令牌——同源请求由服务端会话/客户端在 `session.webRequest` 层注入头，或改用服务端下发的 HttpOnly 会话 Cookie（推荐后者，渲染进程完全不接触令牌）。
- **导航白名单**：只允许配置的服务端源与其同源跳转；外部链接交给系统浏览器；拒绝 `will-navigate` 越界与 `setWindowOpenHandler` 新窗口。
- **证书**：绝不忽略证书错误（不实现 `certificate-error` 的放行）；自签证书场景要求用户显式信任或改用受信证书。
- **离线/故障**：服务端不可达、认证过期、版本不匹配各有独立界面与重试；不缓存业务数据到本地（本期不做离线）。
- **首次配置**：输入服务端地址 → 探活 → 登录 → 记住（地址可改、可清除凭据）。
- **发行**：`electron-builder` 产 MSI/NSIS（Windows 优先），代码签名与自动更新（generic provider）在阶段 2 一起做；更新包必须签名校验。

## 6. 安全清单（必须逐条落实）

- 远程内容视为不可信：渲染进程无 Node、无预加载能力泄漏、无 `remote` 模块。
- 令牌/会话不进渲染进程；不进日志；不进崩溃上报。
- 所有出站只允许配置的源；反代与应用双重校验。
- 多租户：租户/空间来自可信认证结果，绝不从请求体读取（现有 INV-07 不变）。
- 客户端不做「自动信任任意地址的证书」这类便利性妥协。

## 7. 分阶段与验收

| 阶段 | 内容 | 验收 |
|---|---|---|
| P1 | `CORE_API_HOST`、静态托管 + SPA fallback、Bearer 令牌认证、安全响应头 | 远程机器用令牌访问 UI 与 API 全链路可用；未带令牌 401；回环开发模式行为不变；静态路径穿越被拒 |
| P2 | Electron 壳：配置、探活、登录、托盘、离线/过期界面、导航白名单 | 双击安装后只需地址 + 登录即可使用；断开服务端有明确状态；外部链接走系统浏览器 |
| P3 | OIDC 登录 + 多用户 + 自动更新与签名 | 多用户各自空间隔离；更新包签名校验通过 |

## 8. 明确不做

- 本地内嵌 Postgres（那是「本地优先」桌面端，另一条路）。
- 离线编辑与本地缓存业务数据。
- 客户端自带一套独立 UI（本期复用服务端 UI，避免两套实现漂移）。
- CORS 开放给任意来源。

## 9. 风险

- **A1 是部署级共享令牌**：能访问即拥有该租户/空间的全部角色，只适合单团队内网；对外必须尽快进到 A2。
- **服务端托管 UI 意味着 UI 与服务端同版本**：客户端需要版本握手，避免「新 UI 打旧 API」。
- **Electron 加载远程内容**是常见攻击面，安全清单不能打折；一旦允许任意导航或注入 Node 能力，等于把桌面权限交给远端页面。
- 反代配置（TLS、超时、请求体上限）不在应用内，需在部署文档里固定下来。
