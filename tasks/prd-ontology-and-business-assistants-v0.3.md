# PRD v0.3：本体生成助手与业务实践助手

日期：2026-09-29。状态：评审稿；本轮产出需求文档，尚未实现本文新增功能。

首个业务 MVP：AI 造价师报价。当前按电气安装中的电缆桥架起草；“桥梁”与“桥架”的领域澄清及图纸量算范围见 §12。本文保留总体产品与造价验收；阶段 A 的通用能力另见[通用双助手 Core PRD](prd-generic-assistants-core-v0.3.md)。当前文档位于 feat/electrical-costing-poc，不代表通用实现也放在该分支。

## 1. 产品定位与本次决策

产品提供两个相连的助手。本体生成助手把行业资料整理成可审核、可发布、可挂载的行业资产；业务实践助手使用这些资产和客户数据完成具体任务。首个任务是客户提交真实项目并提出报价要求，系统输出经核验、可解释、可复核的报价单。

用户最新要求：“桥架的本体，尤其规则和动作函数，让客户拿真实项目作为 input 提问，AI 给出合格报价”；“MVP 核心是 AI 造价师报价”。本体建设应覆盖这条任务需要的对象、属性、关系、规则、动作与实例。

按用户最新决定分两阶段：**A 补足通用能力与公共前端，独立验收后合入 main；B 造价专属分支同步该主线版本，再完成桥架报价 MVP 与专属前端。** 其他活动场景分支同步同一通用基线并验证兼容性。

两个助手均有可操作前端，分别验收。A 必须从资料生成候选、审核发布行业包，再执行有核验与来源的业务任务，不能只交空壳或预写行业包。B 的主要业务验收是合格报价，复用 A 的建模能力生成所需桥架资产；不要求先完成整个桥架行业的自动建模。客户函数、真实价表与配对样本的核对可提前开展，不改变通用代码先进入 main 的顺序。

## 2. 目标、用户与输入输出

### 2.1 产品目标

1. 行业维护者能从资料提出并修订本体、规则和动作候选，发布可挂载的行业包。
2. 客户能上传项目资料、提出报价要求、补齐关键参数，取得逐项报价与费用范围说明。
3. 每个报价数字能追溯到确认输入、价格与规则版本、函数版本和计算结果。
4. 在约定配对样本上与人工报价逐行比较，差异分类可解释，业务通过有签核记录。
5. 新客户通过映射和适配接入；新行业通过资产与必要扩展挂载，通用 Core 无行业硬编码。

| 用户 | 主要任务 | 权限边界 |
| --- | --- | --- |
| 行业维护者／专家 | 建模、术语消歧、规则确认、定义发布、行业包维护 | 只能操作授权行业与空间 |
| 业务用户／造价师 | 建项目、提交资料、确认参数、请求报价、复核与导出 | 项目范围内操作；不能自行发布全局行业定义 |
| 复核者 | 审查业务口径、差异与结果，签核报价 | 签核权限与普通查看权限分开 |
| 部署维护者 | 挂载后端、客户函数、模型、权限与运行配置 | 技术配置不成为普通用户报价前置操作 |

### 2.2 两助手的输入输出

| 助手 | 输入 | 输出 |
| --- | --- | --- |
| 本体生成助手 | 行业边界、代表性业务问题、规范／术语／表格／说明、已有定义、专家修改 | 类型／属性／关系／规则／动作候选及来源；发布的行业包版本；实例候选；独立标记的合成样例；验证记录 |
| 业务实践助手（A 通用） | 已发布行业包、客户项目资料、自然语言要求、确认参数、可用任务与已注册函数 | 缺项与冲突；固定版本任务输入；事实／规则／查询／计算结果；核验、来源、历史和通用导出 |
| 业务实践助手（B 造价） | 以上通用输入，加桥架资料、权威价格与计价口径、报价函数 | 逐项报价、费用和合计；报价解释与依据；业务复核、历史差异及报价导出 |

真实实例来自项目资料、观测或人工录入。生成的示例实例必须标记“合成”，不会自动成为客户事实、价格或工程量。

## 3. 核心流程与资产边界

### 3.1 两条操作链

~~~mermaid
flowchart TD
    A[行业资料与业务问题] --> B[本体生成助手：建模候选]
    B --> C[专家编辑、校验、确认]
    C --> D[发布行业包版本]
    D --> E[业务实践助手：项目挂载]
    F[客户清单、规格和项目要求] --> E
    E --> G[实例与参数候选、消歧和补参]
    G --> H[确认输入及价格规则快照]
    H --> I[已注册报价动作]
    I --> J[确定性计算、硬核验]
    J --> K[报价表、解释、溯源及业务复核]
    K --> L[经确认的规则或评测改进提案]
    L --> B
~~~

反馈生成修改提案，不能直接改写已发布行业包或旧报价。用户正在看的项目和报价始终显示所用资产版本。

### 3.2 规则、动作与函数

| 层次 | 保存什么 | 示例与约束 |
| --- | --- | --- |
| 行业包 | 对象、属性、关系、单位、术语、身份策略、已确认的通用规则、动作声明与能力要求 | “报价行引用规格”“某类规则要求一个字段”；不保存客户连接串、实时价格或任意脚本 |
| 客户扩展 | 客户专属规则、价格口径、费用范围、审核策略 | 标明适用客户与版本，不能冒称行业标准 |
| 动作声明 | 动作名称、输入输出、适用对象、前置条件、权限、证据和副作用要求 | 如“生成桥架报价”；声明本身不证明已有可执行实现 |
| 领域计算扩展 | 经审查测试的版本化函数与输入输出契约 | 如 costing.quote；数值由确定性实现给出 |
| 客户适配与映射 | 客户列名、单位映射、服务协议、具体 I/O 与来源范围 | 与行业语义及报价页面分开挂载 |
| 项目数据 | 实际实例、原文、价格快照、身份裁决、参数确认与报价 | 按客户／项目隔离，不打包进共享行业资产 |
| 通用 Core | 运行、权限、预算、取消、审核、版本、工件、证据、核验与发布 | 不含桥架材料名、客户表列、实际税率或金额公式 |
| 公共前端与场景界面 | 公共部分提供双助手、资料／审核／任务／证据组件和挂载入口；场景部分提供专业表单、结果展示与导出 | 公共框架不判断行业名；桥架参数、计价口径和报价表在场景组合入口挂载 |

助手可以建议动作契约，不能把模型生成的代码直接执行。执行引用已注册、经授权的函数版本。没有实现时显示“动作尚不可用”；发布语义定义与启用报价能力是两个状态。

### 3.3 首个行业的建模范围

候选最小对象包括 Project／Inquiry、InquiryLine、Product／Specification、PricingContext、PricingRule、Quote／QuoteLine。行业专家确认最终命名、粒度与身份策略，当前示例不等于行业标准。

候选关系包括项目包含清单行、行引用规格、报价引用输入修订和价格口径、报价行对应原清单行、规则与参数引用依据。桥架直线段、盖板、配件、支吊架的覆盖及供货／安装／运输等费用范围需签核。

规则至少覆盖关键参数完整性、规格适用性、单位与计价口径、价格有效性、费用范围及明确例外。金额计算不由语言模型执行。材质、尺寸、板厚、表面处理、标准长度、损耗与税费均不填未经确认的默认值。

## 4. 用户故事与验收

以下是总体产品故事，不是已创建的 GitHub Issue。阶段归属见 §10；混合故事的通用机制先在 A 独立完成，报价验收在 B 完成，不用一个完成标记混淆两者。通用查询／规则／检索／循环的细化验收见阶段 A PRD。最后一项为整栈 E2E；所有 UI 故事均须在浏览器核验，新增代码须通过适用 lint、typecheck 和回归。

### US-001：进入两个助手
**描述：**作为用户，我希望一眼看懂两个助手的用途并进入我的工作。
- [ ] 页面有“本体生成助手”和“业务实践助手”两个明确入口，切换保留各自草稿。
- [ ] A 的业务首页显示项目、新建项目和当前已挂载任务；本体首页显示行业包、创建行业包、继续建模。B 挂载“AI 造价师／请求报价”入口。
- [ ] 空态写清所需资料和下一步；服务不可用时保留页面并给出可重试的中文说明。
- [ ] 在浏览器核验入口、空态、切换、刷新和权限状态。

### US-002：建立有业务边界的行业工作区
**描述：**作为行业维护者，我希望先说明业务问题，再开始生成行业资产。
- [ ] 可填写行业范围、目标任务、适用地区／时间与参考定义；必需项缺失时给出定位提示。
- [ ] 保存后有稳定工作区标识和草稿修订，刷新可恢复。
- [ ] 至少记录一个目标业务问题；A 以交通／工业合成任务验收，B 的桥架包包含“从项目资料形成可复核报价”。
- [ ] 在浏览器核验创建、编辑和恢复。

### US-003：导入行业资料并看到解析状态
**描述：**作为专家，我希望上传资料并知道哪些内容已读取。
- [ ] 首期支持 UTF-8 文本、JSON、CSV 和 XLSX；文本层 PDF 的支持范围单独标注，格式不支持时明确提示。
- [ ] 资料列表显示文件、修订、类型、处理阶段、已解析数量及失败项，不把部分解析写成全量成功。
- [ ] 资料能按 sheet／row／cell 或原文片段打开；扫描件或 DWG 不以“已上传”冒称已量算。
- [ ] 在浏览器核验正常导入、失败、部分成功和原文对照。

### US-004：从资料提出本体定义候选
**描述：**作为专家，我希望助手提出对象类型、属性和关系的建议，减少从零建模的工作。
- [ ] 候选包含名称、业务含义、类型／单位或端点、资料来源、建议理由与冲突提示。
- [ ] 能区分“新增对象类型／属性”与“新增某一条项目记录”，不会混成实例候选；专业术语来自挂载资产。
- [ ] 生成失败可重试，已有人工修改不会被静默覆盖；缺来源的建议标记待确认。
- [ ] 在浏览器核验候选列表、来源、冲突和生成前后的草稿差异。

### US-005：编辑、消歧与审核本体定义
**描述：**作为专家，我希望合并同义术语、拆分错误类型并确认定义。
- [ ] 可编辑类型、属性类型／单位、关系端点及术语；合并和拆分展示受影响定义。
- [ ] 同名不同含义保持独立；标识冲突、悬空关系端点与错误单位阻断发布。
- [ ] 与已发布版本的差异可查看；破坏兼容性的修改需要明确修订策略。
- [ ] 在浏览器核验编辑、拒绝、冲突和差异。

### US-006：生成并审核规则候选
**描述：**作为专家，我希望把规范和经验变成有来源的规则候选。
- [ ] 候选展示条件、结论、例外、适用范围、来源、版本及支持状态，允许人工修订。
- [ ] unknown、冲突和明确 false 分开；不支持的 OR／关系前提／递归保持“尚不能执行”。
- [ ] 候选可保存，但只有完整通过语义与执行能力校验的规则能启用；不得删除条件换取通过。
- [ ] 在浏览器核验规则原文、例外、缺信息和不支持状态。

### US-007：定义动作并绑定已注册能力
**描述：**作为维护者，我希望行业资产说明可执行的业务动作。
- [ ] 动作草稿展示输入输出、前置条件、权限、证据要求和副作用类别。
- [ ] 可绑定授权的已注册函数版本；未绑定或契约不兼容时显示“不可执行”及原因。
- [ ] 模型候选不自动注册代码，不接受任意脚本、任意 URL 或未授权调用。
- [ ] 在浏览器核验动作声明、可用性、未绑定和不兼容状态。

### US-008：按已确认定义抽取实例
**描述：**作为用户，我希望从实际资料生成符合行业定义的实例候选。
- [ ] 抽取请求使用固定版本的类型、属性、关系、单位和规则约束；不得仅在响应之后才做 Schema 校验。
- [ ] 属性保留原始值、规范值与来源位置，数量和尺寸不得先经有损浮点转换。
- [ ] 未知字段或无法确认的关系端点进入待处理，不由模型自行发布。
- [ ] 在浏览器核验来源对照、字段错误、关系端点和待处理项。

### US-009：生成独立标记的测试实例
**描述：**作为维护者，我希望用示例检查定义和动作契约。
- [ ] 可基于草稿或发布版本生成合成样例，来源类型与“合成测试”标识持续可见。
- [ ] 样例可覆盖缺参数、同名异物、冲突、错单位与缺能力，工作台显示规则匹配和已注册动作试算；B 补缺价等报价反例。
- [ ] 合成样例与真实项目隔离，不自动成为真实报价依据。
- [ ] 在浏览器核验生成、验证和隔离。

### US-010：确认实例身份并审核发布
**描述：**作为复核者，我希望避免同名对象和重复资料污染业务数据。
- [ ] 候选可匹配已有实体或创建后明确绑定新实体；裁决记录理由与修订。
- [ ] 实例、关系和关键属性可对照来源审核，批准与发布为可区分的操作。
- [ ] 原始记录保持稳定行标识；实体合并不会删除独立业务记录。B 验证同规格多行不丢数量或项目位置。
- [ ] 在浏览器核验绑定、冲突、拒绝及发布后的可读状态。

### US-011：发布并导出行业包
**描述：**作为维护者，我希望得到业务助手可挂载的行业资产版本。
- [ ] 发布包含定义、术语、身份策略、规则声明、动作契约、能力要求和经确认的合成样例。
- [ ] 版本不可变，能查看来源与差异；客户原文、真实价格、连接密钥和身份裁决不进入共享包。
- [ ] 展示“语义已发布”和“当前部署可执行哪些动作”；包可导出并在授权工作区重新挂载。
- [ ] 在浏览器核验发布阻断、版本查看、导出与挂载入口。

### US-012：创建客户项目并挂载行业包
**描述：**作为业务用户，我希望创建客户项目，并使用指定行业资产完成任务。
- [ ] 可建立项目、输入业务目标、选择已发布行业包；页面显示项目、行业、客户范围和所用版本。
- [ ] A 按动作契约检查所需规则、函数、输入与映射；B 追加权威价格和计价口径检查。缺项列出原因和下一步。
- [ ] 已有项目不自动切到行业包新版本，切换形成新修订并展示影响。
- [ ] 在浏览器核验建项目、挂载、未就绪和版本切换。

### US-013：导入项目资料并整理清单
**描述：**作为造价师，我希望实际清单成为这次报价的输入。
- [ ] XLSX／CSV 可选择工作表并确认／调整列对应关系，显示原行号、名称、规格、数量和单位；JSON／文本进入相同审核流程。
- [ ] 首期清单模板和可解析表结构明确可见；多级表头、合并单元格等未支持结构定位提示，不自动错猜后宣称解析成功。
- [ ] 显示总行、已解析、待确认、无法处理、拟计价和排除数量；排除须有理由。
- [ ] 重复导入按文件修订处理；跨页仍保持行完整，新资料不能查询到另一项目的示例数据。
- [ ] 在浏览器核验上传、分页、重复导入、失败行和项目隔离。

### US-014：补齐并确认报价参数
**描述：**作为造价师，我希望解决缺值和歧义后再报价。
- [ ] 关键字段展示原文、当前值、单位、来源和 pending／confirmed／conflict 状态。
- [ ] 可编辑规范值与批量确认符合条件的行，记录确认人、时间和修订；改值后需重新检查。
- [ ] 缺数量、未知单位、规格冲突和未确认关键参数阻断计价，不默认为零或常见值。
- [ ] 在浏览器核验逐字段修改、批量确认、来源定位与阻断。

### US-015：通过自然语言提出项目任务
**描述：**作为客户，我希望说“给这个项目报价”就能进入报价流程。
- [ ] 报价工作区有问题输入与报价快捷入口，当前项目和资料范围明确可见。
- [ ] 能识别已支持的报价、缺项检查和报价解释任务；不支持的任务给出范围说明。
- [ ] “更换规格／税费口径后重新报价”等请求先呈现具体参数变更供确认。
- [ ] 在浏览器核验普通提问、缺项澄清、修改确认与范围外问题。

### US-016：确认价格与计价口径
**描述：**作为造价师，我希望清楚知道报价包含什么、按哪个版本计算。
- [ ] 展示价格基准日、版本、生效范围、币种、计量单位、含税口径、费用范围和函数版本。
- [ ] 客户规则、行业规则与专家建议分来源；价格过期、缺配件价或口径冲突时明确阻断。
- [ ] 可选择授权价格来源及快照；缺价按权威函数契约，由授权维护者补录、导入或更新价格源形成新版本，项目采用后重新确认并计算。首期至少提供一条实际可用的补价路径，不要求另建通用价表平台。
- [ ] 米／根／套等换算需有长度或组成依据；税费与舍入阶段采用客户确认版本。
- [ ] 在浏览器核验选择、确认、缺价、过期和口径冲突。

### US-017：调用确定性报价动作
**描述：**作为用户，我希望对已经确认的输入得到可复核的计算结果。
- [ ] 输入以不可变快照绑定批准行、参数、行业／规则／价格版本、函数版本及完整性。
- [ ] 正常请求通过已注册报价动作执行，保存逐行结果、调用记录、失败和覆盖情况。
- [ ] 客户函数不可用或未获确认时不给正式报价；替身只能产出显式合成结果。
- [ ] 数量、金额和币种遵守明确精度及舍入契约；内部浮点函数的边界需对照确认。

### US-018：核验并发布报价
**描述：**作为复核者，我希望页面中的数字与授权计算结果严格一致。
- [ ] 结果字段形成类型化断言并绑定证据；显示、核验、发布和持久化采用同一版本。
- [ ] 数值、行标识、单位／币种、规则／价格／函数版本或完整性不匹配时阻断发布。
- [ ] 撤回、过期或错范围的依赖不能作为新报价依据；模型概率不能替代程序核验。
- [ ] 覆盖不足只显示明确标记的部分结果及未覆盖项，不显示“完整项目合计”。

### US-019：阅读可操作的报价结果
**描述：**作为客户，我希望得到专业报价表并知道接下来能做什么。
- [ ] 表格包含稳定行号、名称、规格、数量、单位、单价、金额和状态；税费／配件／费用按确认范围展示。
- [ ] 显示范围、币种、含税口径、覆盖率、待处理项与核验／业务审核状态，金额精度不被 UI 改写。
- [ ] 可分页、定位问题行、查看差异及导出；空表和失败展示具体原因，不仅展示错误码。
- [ ] 在浏览器核验长清单、合计、部分失败和刷新回读。

### US-020：逐项查看业务依据
**描述：**作为造价师，我希望点击数字就能复核它的来源。
- [ ] 从任意报价行展开“原文／单元格→确认参数→适用规则和价格→函数调用→结果”。
- [ ] 能看到来源修订、确认记录和计算版本；事实支撑与规范原文分别展示覆盖状态。
- [ ] 证据缺失或截断时显示限制，不能用模型解释补成完整证明；不展示模型内部思维链。
- [ ] 在浏览器核验数字定位、原文对照、缺证据和跨范围拒绝。

### US-021：修改、重算、取消和恢复
**描述：**作为用户，我希望修改输入后生成新报价，同时保留之前结果。
- [ ] 变更输入、价格或行业版本产生新修订；重算前展示变化，旧报价保留原快照和证据。
- [ ] 执行中有阶段进度和取消入口；重试沿用同一逻辑动作标识，不能重复生成计价动作。
- [ ] 刷新／进程重启可读回持久结果；历史回读与固定版本复算分别标注能力。
- [ ] 在浏览器核验修改、取消、重试、历史与恢复。

### US-022：导出并复核报价
**描述：**作为客户和造价师，我希望将结果用于审核并与人工结果比对。
- [ ] 可导出 XLSX 和结构化 JSON，包含明细、范围、版本、状态及溯源索引；导出与已核验页面一致。
- [ ] 配对人工报价按稳定行标识比较参数、单价、数量、费用、税费与金额差异。
- [ ] 复核者记录接受／退回、原因和签核人；阈值来自签核口径，未签核不得显示“业务通过”。
- [ ] 在浏览器核验导出、差异、退回与签核。

### US-023：验证行业资产和客户适配可复用
**描述：**作为平台维护者，我希望资产能用于后续客户与行业。
- [ ] A 在交通和工业合成任务中验证同一框架，并以不同列名／单位映射核对结果；通用 Core 和双助手框架不新增行业分支判断。
- [ ] B 在同一桥架语义版本下挂载两套合成客户映射，批准后的同口径报价结果一致。
- [ ] 动作、数据后端与运行时由明确契约装配；不兼容组合拒绝并说明原因。
- [ ] 共享资产导出不含私有项目实例、价格和密钥；完成适用边界测试。

### US-024：两助手整栈 E2E 验收
**描述：**作为测试负责人，我希望正常用户操作证明从行业建设到报价的完整产品链。
- [ ] A 先通过[通用 PRD](prd-generic-assistants-core-v0.3.md)的独立 E2E，记录验收后的 main 提交；B 同步该版本并保留通用回归。
- [ ] 自动浏览器测试从原始合成资料生成定义／规则／动作候选，人工编辑确认后发布包并挂载项目。
- [ ] 在同一测试中导入清单、完成身份和参数确认、提出报价要求、调用注册函数、核验发布、展开来源并导出。
- [ ] 覆盖缺价阻断与补齐后报价、金额／行绑定篡改被拒绝、输入修订后的新旧报价回读及跨客户访问拒绝。
- [ ] 使用真实 UI／API／持久层和正常任务分派；不预置候选、已发布结论或最终答案，不手动启动 Controller。
- [ ] CI 可重复执行并清理自建数据和资源；受控模型／合成函数验证与真实模型／客户样本验收分别报告。

## 5. 功能要求

以下要求覆盖总体产品及报价 MVP；A 的行业无关要求单独列在通用 PRD 中。涉及清单计价、金额、价格与报价签核的业务含义归 B，其审核、版本、执行和证据机制归 A。

- FR-1：系统必须提供两个有明确用途和独立工作状态的助手入口。
- FR-2：系统必须保存行业工作区的业务范围、目标问题和资料修订。
- FR-3：系统必须按已支持格式解析资料并保留原始位置。
- FR-4：系统必须从资料生成本体定义候选及其依据。
- FR-5：系统必须区分定义候选、真实实例候选和合成实例。
- FR-6：系统必须允许专家编辑、拒绝、合并或拆分定义候选。
- FR-7：系统必须校验类型、属性、单位和关系端点的一致性。
- FR-8：系统必须显示规则候选的条件、结论、例外与适用范围。
- FR-9：系统必须阻止尚不支持的规则表达被启用。
- FR-10：系统必须保存动作声明的输入输出、前置条件与权限。
- FR-11：系统必须仅执行已注册并授权的函数版本。
- FR-12：系统必须让抽取请求获得当前固定版本的行业约束。
- FR-13：系统必须保存实例身份裁决与审核记录。
- FR-14：系统必须发布不可变行业包版本。
- FR-15：系统必须分别显示语义发布状态与部署执行能力。
- FR-16：系统必须隔离共享行业资产和客户项目数据。
- FR-17：系统必须为客户项目绑定确定的行业资产版本。
- FR-18：系统必须使本次项目的实际批准数据可由业务动作读取。
- FR-19：系统必须报告清单各处理阶段的行数和覆盖情况。
- FR-20：系统必须记录关键字段的原始值、规范值、来源和确认状态。
- FR-21：系统必须阻断缺参数、错单位、缺价和计价口径冲突。
- FR-22：系统必须将自然语言报价请求转为当前项目的受支持业务任务。
- FR-23：系统必须在执行参数变更前呈现待确认修改。
- FR-24：系统必须固定报价输入、价格、规则和函数的版本引用。
- FR-25：系统必须由确定性函数产出报价金额。
- FR-26：系统必须将结果字段绑定到可核验的计算证据。
- FR-27：系统必须在发布前校验输入、来源、依赖与结果完整性。
- FR-28：系统必须展示逐项报价和范围明确的合计。
- FR-29：系统必须提供从报价字段到原始依据的交互溯源。
- FR-30：系统必须按修订保留旧报价和其原始证据。
- FR-31：系统必须支持有界任务取消与幂等重试。
- FR-32：系统必须导出与已核验版本一致的报价。
- FR-33：系统必须保存人工报价比较和业务签核决定。
- FR-34：系统必须将项目反馈形成行业修改提案而非直接覆盖已发布资产。
- FR-35：系统必须通过场景组合入口挂载专业页面，不在公共双助手框架内按行业名称分支。

## 6. 前端设计要求

### 6.1 信息架构

| 工作区 | 主要页面 | 用户在这里完成什么 |
| --- | --- | --- |
| A 本体生成助手 | 行业包首页、资料、定义编辑、规则与动作、实例审核、验证与发布 | 建行业、看来源、改候选、验证、发布和挂载 |
| A 业务实践助手公共框架 | 项目首页、资料与字段确认、任务入口、通用结果、证据与历史 | 挂载资产、提问、补参、执行任务、查看核验与依据 |
| B 造价场景工作台 | 桥架清单、规格确认、计价口径、报价表、金额依据、差异与签核 | 报价、补价、复核、导出和重算 |

主页面围绕行业包和项目组织，不要求业务用户操作数据库、runtime、MCP、模型 binding 或工具 JSON。技术配置放在有权限的维护区；用“缺少报价函数／价格资料”等业务原因解释不可用。

公共框架提供场景入口、字段审核、任务状态、类型化结果和证据组件；造价模块挂载专业表单、报价表、业务校验提示与导出。定义包仍只保存声明，不夹带页面代码。未配置造价模块的主线不会默认显示不可操作的报价按钮。A 必须已有可用任务和结果页面，不能只留下插件接口。

### 6.2 本体生成工作台

左侧为资料与来源，中间为可编辑类型／属性／关系或规则列表，右侧为详情、来源对照和修改建议。列表视图是必需入口；图谱可辅助理解关系，不能替代编辑与审核。

顶部显示行业范围、草稿／发布版本及下一步。流程为“准备资料→生成候选→编辑确认→验证→发布”。仅发布成功才出现挂载入口；执行能力未就绪时仍明确显示缺项。

### 6.3 B 的报价专属工作台

顶部显示项目、输入修订、行业版本和业务状态；主体为清单／报价表，旁边为需求输入、澄清和依据面板。流程为“项目资料→参数确认→计价口径→生成报价→核验与复核→导出”。

报价表中数字从已核验结果渲染，解释不得另生成未经核验金额。点击字段打开原文与依据；支持按问题状态定位。最终成果始终是报价单，聊天记录是任务交互和解释载体。

### 6.4 必需状态

| 状态 | 页面必须展示的内容与操作 |
| --- | --- |
| 首次进入／无资料 | 输入要求、可用格式、示例性质和创建／上传入口 |
| 未配置／未就绪 | 缺少什么、由谁处理、可继续做什么 |
| 处理中 | 当前阶段、已处理与失败数量、取消入口 |
| 待确认／冲突 | 原文、当前值、冲突原因和具体修正入口 |
| 部分成功／不完整 | 已覆盖与未覆盖行；不显示完整合计 |
| 系统核验通过 | 已核验版本、费用范围、业务审核状态和来源 |
| 业务接受／退回 | 签核人、决定、原因和需修改项 |
| 失败／权限不足／过期 | 中文原因、可恢复动作及保留的历史；技术细节可折叠 |

首版需在桌面浏览器验证长表、来源面板、键盘表单、空态和错误态；窄屏允许明确的表格滚动，不遮挡确认和取消操作。

## 7. 合格报价与成功指标

### 7.1 四层验收

| 层次 | 判断条件 | 不能替代的下一层 |
| --- | --- | --- |
| 内部机制验证 | 合成数据／受控模型／替身函数的正常流程和反例通过 | 不证明客户金额正确 |
| 系统核验通过 | 行、字段、单位、币种、版本、来源和完整性与授权结果一致 | 不证明业务规则和原始资料正确 |
| 真实样本业务通过 | 与同输入、同口径人工结果逐行比对并获授权造价师签核 | 不等于客户正式生产验收 |
| 客户／内部 MVP 验收 | 按约定样本、范围、输出与验收人记录结论 | 不自动扩展到未覆盖品类或格式 |

“合格报价”须具备确认输入、权威计价依据、完整覆盖、系统核验与业务通过记录。未达到某层时显示实际状态，不能只显示“AI 报价成功”。

### 7.2 指标及通过口径

| 维度 | 测量方法 | 本版要求 |
| --- | --- | --- |
| 建模效果 | 候选与专家参考定义的语义对齐、遗漏、错误、人工修改耗时 | 固定目标任务和参考版本；阈值经评测基线和专家确认 |
| 包可用性 | 发布后挂载、实例抽取、规则和动作契约验证 | MVP 所需已确认资产须可挂载并完成目标报价任务 |
| 提参质量 | 关键字段原始值／规范值与专家结果逐字段比较 | 发布报价前所有必需字段已确认；候选准确率独立报告 |
| 金额质量 | 同口径人工报价逐行与分类差异 | 容差、舍入与通过标准由专家确认，不预设 1% |
| 完整性 | 输入、处理、计价和排除行的对账 | 正式完整报价无静默遗漏；排除有确认理由 |
| 溯源覆盖 | 从每个报价行的关键字段展开依据 | 缺失或错绑定阻断相应正式结果 |
| 鲁棒性 | 缺价、缺参、错误金额、撤回、错版本、错范围、取消 | 验收反例不得被错误发布为通过 |
| 规模与成本 | 行数、并发、耗时、模型用量、失败与重试 | 测试至少含 1001 行合成清单；真实容量按实测报告 |

调参样例与保留验证样例分开。参考本体是专家针对业务范围确认的版本，可以存在合理替代定义；不宣称唯一最优本体。小样本结果不宣称行业泛化。

## 8. MVP、后续能力与非目标

**A 通用交付到 main：**可操作双助手与挂载边界；资料解析、定义／规则／动作候选和行业包发布；实例抽取、消歧与字段确认；自然语言业务任务、受支持的关系／规则查询、结构化查询、文档检索及有界执行；注册动作、类型化结果、核验与完整溯源；修订、历史、取消和通用导出。具体有限范围与独立验收见通用 PRD，不依赖客户价表或报价函数。

**B 造价 MVP：**造价分支同步 A 的 main 版本后，开发桥架行业包、客户规则与清单适配、确定性报价函数与权威价格、专业前端、报价解释／导出／比对／签核，完成两助手在真实项目上的联调与业务验收。

**后续平台能力：**更广行业覆盖、更多数据后端／检索实现、更广布尔与规则表达、受控递归。按明确内部研究目标可独立启动；不要求等待客户订单。已确认的报价需求超出 A 范围时，先独立补通用能力并合入 main，再由 B 同步，不能删规则条件绕过。

**本期不承诺：**完整行业标准自动认证、通用 OWL、无限深度／容量、全局最优保证、模型自动执行生成代码、全自动发布本体、重构客户完整系统、自动对外发送报价或写客户生产系统。首期品类及图纸量算覆盖由 §12 的签核确定。

## 9. 技术与运行约束

- 使用现有 TypeScript、通用运行／审核／工件／证据能力；包数量由职责和已有约定决定，不为每个页面或客户新建包。
- 行业、客户映射、报价扩展、适配器、runtime 和数据后端显式装配；本地和 MCP 共用授权与领域服务。
- 前端也遵守同一边界：公共双助手和证据组件进入 main，造价字段、专业表、计算解释与报价导出由场景模块挂载；不以合并通用能力为由混入客户实现。
- 模型可选数据工具仍为 ontology_lookup、data_query、document_search、web_search；报价动作通过注册 compute 执行，不新增万能工具。
- 固定报价任务可以不调用 JEV 或动态 Agent；有不确定路由时才选择性决策。模型判断不能改变权限、预算或发布口径。
- 本次批准的项目输入必须真实进入业务动作的数据范围。导入原文、发布语义事实和更新物理查询表是不同阶段，不能用启动时示例快照替代客户资料。
- 复用现有可查询存储与控制／证据存储；数据库或向量库由需求挂载，DataOS 仅视为数据中台。
- 数量与金额保留精确表示及明确单位／币种；客户函数内部浮点精度需确认，外围 Decimal 不能恢复已丢失精度。
- writer、硬核验、证据种类的发布有效性、持久化和前端一起设计。增加表格展示不等于已支持计算证据。
- 批次、分页、文件／行上限、模型并发、超时和输出大小必须有界；截断显式不完整。重复执行、取消、恢复不重置共享预算。
- 所有读取、状态、缓存、模型上下文与后台任务保持客户／项目隔离；实例与规则使用匹配的有效时间和记录版本。

## 10. 实施顺序与依赖

| 阶段 | 开发与合并目标 | 退出条件 |
| --- | --- | --- |
| A 补足通用功能 | 优先复用通用研发工作线，按能力审查已有 WIP；通用后端、公共前端与行业无关验收通过 PR 合入 main | 两个合成行业、不同客户映射、注册示例动作及正常双助手 E2E 通过；记录 main 提交、迁移／配置说明和 README |
| A→B 同步门槛 | feat/electrical-costing-poc 及其他活动场景分支获取并同步上述 main 提交 | 明确使用的基线，执行受影响回归；现有未提交工作被保留，不带入未完成的实验分支 |
| B 完成造价 MVP | 在现有 feat/electrical-costing-poc 开发行业／客户／计算扩展与专属 UI | 合成闭环先通过；权威函数、价格及配对样本就绪后，通过真实报价比对与业务签核 |

### 10.1 总体故事如何分阶段

| 总体故事 | A：通用交付 | B：造价交付 |
| --- | --- | --- |
| US-001～011 | 两助手、行业工作区、候选／审核／发布、实例和动作机制 | 桥架资料与专家确认的本体、规则、动作、术语及样例 |
| US-012～015 | 项目挂载、解析与映射、字段确认、受支持任务入口 | 桥架清单、拟计价范围、报价字段及报价意图 |
| US-016 | 依赖可用性和版本引用机制 | 权威价格、补价、计量换算、税费和费用范围 |
| US-017～018 | 注册 compute、输入／结果工件、核验与发布有效性 | 报价函数适配、金额证据、报价口径和覆盖校验 |
| US-019～021 | 通用结果、证据面板、修订、历史、取消／恢复 | 专业报价表、费用构成、金额依据与重算差异 |
| US-022 | 通用工件导出和审核记录能力 | 报价 XLSX、人工价格比对及造价业务签核 |
| US-023～024 | 行业无关替换验证与 A 独立 E2E | 两客户报价映射验证与最终报价 E2E |

A 不用真实价表、客户函数或客户签核证明主线可用；B 不能用 A 的合成计算代替正式报价验收。A 的独立验收与 B 的业务验收分别记录，不把“Core 合入 main”写成“报价已交付”。

进入 A 实施前冻结该阶段的支持格式、任务、规则子集、循环上限和退出条件，完成对应 SPEC／任务拆分。有限功能须真正跑通；未覆盖的研究目标另列，不让“补足通用能力”变成没有结束条件的全部平台研发。日期与资源投入未再次确认前不增加对外工期承诺。

B 发现可复用缺口时，独立提交／测试通用修复，先合入 main，再同步回造价分支；已有暂存修改也需依赖核对和回流，不能长期分叉维护。场景新增资产可经脱敏和独立验收另行回流，客户私有实现不自动合并主线。具体同步和 WIP 处理见分支管理。

客户函数、价格口径、配对样本和图纸覆盖可在 A 期间继续 discovery；它们不阻断 A，未就绪时 B 的真实报价保持“未就绪”。异常回退和未覆盖项由项目负责人与客户确认。
