## 2. 首个产品切片（建议）

家庭能源决策助手：回答“为什么这样用电”，给出可比较、可检查约束的分时调度方案，并在仿真中展示执行效果。设备资源明确后再扩展真实执行。

主要用户：拥有阳台光伏/家庭电池系统的家庭用户。车辆充电并非海报明确要求，只有设备与数据支持时才加入，不把“充电储能”默认等同于电动汽车充电。

建议首个体验：用户提出“希望降低明日购电支出，同时保留指定备用电量”，系统读取当前设备、用电历史、价格及可用天气/发电预测，给出时间表、预测成本、备用电量曲线、依据与不确定性；用户改变备电要求或天气假设后重新比较。

停电风险若没有可靠输入，仅作为用户指定假设或演示事件，不能声称系统预测了真实停电。节省金额在演示中属于仿真估计，不表示实际账单收益。

## 3. 三层交付与状态

| 层次 | 可展示结果 | 进入条件 |
|---|---|---|
| 状态与解释 | 当前能量流、设备约束、历史用电与来源 | 真实读取或明确标记的样例数据 |
| 计划与仿真 | 分时策略、基线对比、约束校验、模拟执行日志 | 模型参数/价格/初始状态有依据；假设明确 |
| 真实执行与回读 | 已确认计划下发、设备状态回读、偏差记录与停止 | 实际设备/插件能力、控制边界及授权明确，另行评审执行入口 |

前两层建议纳入首个可运行场景。第三层是面向赛道完整闭环的目标，需要资源验证；仿真不能标成真实控制。最终参赛要求是否必须实机由活动正式资料确认。

## 4. 家庭能源行业包

| 概念 | 必需语义 |
|---|---|
| Household / Site | 站点、时区、计量边界 |
| Device / Battery / Inverter | 实际设备 ID、额定/可用容量、读写能力及规格来源 |
| PV System | 发电侧设备及测量/预测来源 |
| GridConnection / Meter | 购电与上网方向、允许条件及计量范围 |
| Load / CriticalLoad | 用电设备或负载分组、优先级、可调度能力 |
| Sensor / Observation | 被测对象、测量类型、单位、采样时间、质量与新鲜度 |
| Tariff / TariffInterval | 地区、时区、有效日期、买入/卖出价格和计费口径 |
| Forecast | 预测对象、发布时间、目标时间窗、版本、误差/情景 |
| UserConstraint | 备电要求、使用时间和偏好，来源与有效范围 |
| EnergyPlan / PlanStep | 目标、时段、功率/模式、输入版本、约束结果、可行性 |
| ExecutionRecord | 模拟/真实模式、计划版本、请求/反馈及观察到的结果 |

消歧重点是设备与其多个传感器、来源别名及更换历史，不以 LLM 重新判定所有已经具有可靠 ID 的遥测。必须区分 kW 与 kWh、瞬时值与累计值、SOC 与可用电量、观测与预测、购电与上网。名称相同的传感器不能直接归为同一测点。

显式维护测点覆盖范围，避免总表与其子回路重复计入家庭负载；处理累计电量表归零、缺采样和 unknown/unavailable，不能默认为零。电池容量、功率限制、效率和备电能力来自型号文档或明确的模拟配置；拥有电池不自动意味着支持停电时的离网供电与切换。

大规模时序样本留在数据后端，本体保存定义、映射和关键关系；不把每个传感器采样点都扩成繁重本体对象。物化可先针对聚合、约束状态和计划摘要，保留原始时间窗与数据版本。

## 5. 与通用平台的对应

- 数据后端：Home Assistant 是设备/遥测接入适配器之一，历史数据可进入时序/分析后端；DataOS 仍只是可选数据中台。
- `ontology_lookup`：取得设备含义、能量流关系、指标单位、约束与控制能力。
- `data_query`：读取历史/状态，执行明确登记的只读计算，例如能耗聚合与候选计划仿真。优化/仿真服务有独立输入输出契约，不能让自然语言自行变成任意脚本。
- `document_search`：检索已核实型号的说明书、参数与使用限制；不同型号不得混用。
- `web_search`：仅在需要时补充公开资料。天气/价格等稳定数据源优先用明确的数据适配器，不让普通网页搜索结果直接充当控制输入。
- JEV：识别问题类型、是否缺信息、从已校验候选策略中选择或触发澄清；不直接计算电池充放电轨迹。
- 生成式 LLM：解释需求、组织计划候选和自然语言说明；功率、能量、成本和约束由确定性计算验证。
- Runtime：一次状态查询直接结束；取约束→查时序→仿真比较→解释使用小计划；数据/偏好变化时有界重规划。

## 6. 新增的必要能力与工具边界（待评审）

原 PRD 是读取业务数据的产品，这个赛题要求进一步生成和执行调度方案。必须增加能源计划/仿真领域服务，不能仅用 SQL/RAG 回答后声称完成调度。

方案 A：首版将受限计划计算作为 `data_query` 的显式只读计算操作，由行业包声明、运行时预检，保持四个公共数据工具。方案 B：若这一契约过宽，单独注册 `energy_simulate` 并升级场景工具目录。两者二选一，在 SPEC 前确认；不能运行时偷偷增加工具。

真实执行需要独立受控动作入口，例如接受 plan_id 的执行服务，而不是让 `data_query` 或模型直接调用任意 Home Assistant service。动作入口尚未纳入已接受的四工具只读目录，不因用户给了活动链接就获得设备操作授权。

执行必须区分已计划、已确认、已发送、设备已接受、已观察到生效、失败/已停止。HTTP 成功或模拟状态变化不能当作物理执行成功。Home Assistant 的状态更新与设备 service 调用是不同语义，接入时必须验证。[REST API](https://developers.home-assistant.io/docs/api/rest/)

## 7. 调度与核验要求（研究建议，不是设备参数）

- 输入：初始 SOC/可用容量、设备功率限制、效率模型、历史/预测负载、可用光伏预测、价格时段、备电要求、实际拓扑与支持模式。缺关键参数时不输出伪精确的可执行计划。
- 基线和候选使用相同输入、时间窗、初始状态和明确的期末备电约束；避免靠耗尽电池制造虚假节省。
- 校验功率/容量/备用量约束、时间对齐、能量收支和费用计算；若不允许同时充放电、上网或电网充电，计划不得使用该能力。具体约束以型号和站点配置为准。
- 目标先明确优先级，例如先满足备电与硬约束，再比较购电成本；“最优”仅限声明模型、目标和情景，JEV 评分不证明物理最优。
- 至少比较正常天气、低发电、负载上升、数据缺失/过期等情景。天气/负载预测不是事实，回答和图表标明预测区间/假设。
- 真实执行前重验状态、计划有效期和约束；人工更改/断连/状态过期时按设备允许的方案停止或退回既定模式。详细策略须结合真实接口，不能泛化保证。

## 8. 推荐 Demo 与验收

1. 首页展示一户家庭的实际或明确合成的光储/负载/电网数据，所有测量有单位、时间与来源。
2. 用户给出用能目标和备用要求，系统生成至少一个可行方案，并与明确基线比较。
3. 展示计划曲线、预测成本和约束满足情况；点击结论可追到数据、设备约束、预测版本与计算结果。
4. 改变一个备电要求或天气情景，重算后说明何处改变；需求不可能满足时说明缺口。
5. 在仿真中执行所选计划并展示日志/曲线；实机可用且获授权后增加同接口的真实适配及状态回读。
6. 至少一条异常：传感器过期或不支持某控制模式，系统不能继续把旧计划当当前可执行方案。

按黑客松短周期做一个能源纵向闭环；不把其他行业包、全部数据库或全部运行时适配作为此次展示前提。保留解耦契约，避免为演示重建完整平台。
