## 权威输入

[manifest.json](manifest.json) 是编号、依赖和条件清单；每张卡片定义范围与验收；[coverage.md](coverage.md) 追踪需求。来源均在项目 tasks/，input_sha256 用于发现规格漂移。

工程按当前 PRD/SPEC 独立建设。历史演示代码、数据和测试不是输入依赖或金标；无需启动原型、导出其数据库或保留其接口。LOCAL-048 在公共契约完成后构造新的语义夹具，LOCAL-032/033/034/054 用规格预期验证实现。

## 与 loop-it 的兼容边界

当前已安装 loop-it 默认使用 gh 获取 GitHub 全部 open Issues，并包含提交、PR、合并和关闭流程；它没有在本轮验证可直接消费这些本地文件。新工程目录 `D:/work/ontology` 已是 Git 仓库，origin 为 `https://github.com/Yijtu/ontology.git`；本地任务尚未映射为远程 Issue。

因此不能直接运行裸 loop-it 并声称会执行此本地清单。后续有两条明确路线：

1. 用户要求本地实现时：按指定 LOCAL 文件逐卡读取、实现、测试、审查；不伪造 GitHub 编号，不宣称完成GitHub ship流程。
2. 用户选择GitHub执行时：使用当前已关联的 `Yijtu/ontology`（若用户另有指定则以其为准）创建远程Issue，把本地依赖映射为真实编号并写回manifest；交接给 loop-it 时明确本批编号。不能把 LOCAL-012 当成 GitHub #12，也不能抓到其他open Issue就扩大范围。本次目录迁移不创建远程Issue。

没有读过的参数或本地模式不猜。当前不修改 loop-it 技能，不创建 .loop-state.json；本地manifest与未来GitHub执行检查点属于不同状态系统。
