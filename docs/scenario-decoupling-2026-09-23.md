# 多行业异构数据与框架解耦方案

日期：2026-09-23，按用户最新说明修订。**确定需求是兼容不同行业、不同客户的不同数据结构，持续复用框架；是否新建场景包、普通目录或业务分支，按实际情况决定。** 上一稿将独立 ScenarioPackage 作为默认必建结构，这项要求撤回。

进一步补充：用户明确关注行业资产如何持续积累，并重新评估分支方式。本文建议的默认策略调整为**共享主干 + 版本化行业资产 + 客户配置引用**；短期开发/试验使用分支，长期行业/客户分支仅作特殊交付选择。这是本轮架构建议，尚未执行 Git 或目录调整。

本文是待实施方案。现状见[逆向规格](SPEC-as-built-2026-09-23.md)，缺陷见[修复清单](reviews/2026-09-23-code-review.md)。本轮没有创建分支或执行重构。

## 1. 确定的目标

同一套接入、工具执行、Agent 控制、核验、溯源、权限和预算机制，能够用于不同客户的数据；这些数据不必使用相同表名、列名、主键、关系或行业概念。

当前不要求每个行业单独建立 npm/workspace 包，也不要求一个界面动态切换所有行业或运行时安装插件。使用已有基础能力接入新客户时，改动应集中在语义定义、客户映射、来源配置、必要的适配器与场景代码。通用 controller/gateway/核验/证据/预算不应出现客户表名或能源专属判断。

遇到平台尚未支持的基础能力，可以单独升级公共契约并回归验证；不能承诺任意未知数据都能靠配置完成。

## 2. 区分四种差异

| 差异 | 例子 | 优先处理位置 |
|---|---|---|
| 来源与读取方式不同 | PostgreSQL、DuckDB、业务 API、文件、文档 | 已有 adapter + 来源配置；新读取协议/方言才补 adapter |
| 物理结构不同 | 表/列改名、复合键、宽表/长表、嵌套 JSON、连接路径不同 | 客户 schema/catalog、版本化 mapping；复杂整形用视图或有界预处理 |
| 行业语义不同 | 电池/测点/储能计划，变为道路设施/巡检/工单 | 行业对象、属性、关系、身份、规则和评测数据 |
| 业务任务不同 | 查询统计，变为策略仿真、专属表单或展示 | 场景代码、确定计算 handler、模板与页面；按需形成模块/包 |

新增一张表通常不需要新增适配器；换行业不必换数据库；新分支也不会自动建立这些边界。

## 3. 数据处理链路

结构化数据：客户表/API/文件 → 来源适配与实际 schema → 已确认映射/必要视图或预处理 → 可选行业语义 → 工具查询 → 核验、回答与溯源。

非结构化数据：文档 → 解析/分块/来源位置 → 文档检索；启用本体时，再增加按行业 schema 抽取、消歧、审核发布与规则推理。

普通查询可以直接使用实际 schema、权限与数据工具。共用工具/证据协议，不意味着所有行业要共用一张“大表”或同一套业务对象；本体仍然是可选能力。

### 3.1 每份客户接入配置应说明

1. **来源目录**：可见表/集合/文档、列类型、主键、外键、时间字段、数据范围、权限及来源版本。
2. **语义定义（启用本体时）**：对象、属性、关系、单位、业务含义；不能仅因字段同名而合并概念。
3. **物理映射**：概念对应哪些表/视图，属性对应哪些列/路径；连接键、方向、基数、fanout 上限，以及状态码/单位/时间转换。
4. **身份与消歧**：ID 在哪个来源/租户/类型范围内唯一，是否使用复合键；同名、别名及合并如何确认。
5. **质量与演进**：缺失/未知/冲突如何表达，如何处理 schema 漂移、增量、修订和撤回；旧 run/证据固定映射及语义版本。

模型可提出映射候选，执行使用已确认版本。找不到列、单位含义不明或关系多义时返回缺口，不能临时猜字段继续查询。

### 3.2 验证示例

以下为设计示例，不是已接入的客户数据：

| 数据集 | 原始结构 | 业务语义/适配 |
|---|---|---|
| 能源客户 A | device_reading(device_id, ts, soc_pct) | 电池 ID、时间、SOC；百分数尺度 |
| 能源客户 B | telemetry(asset_key, metric_code, num_value, time_utc) | 经明确的 metric 过滤、视图或预处理取得 SOC；若值为 0–1，显式换算尺度 |
| 交通客户 C | road_asset + inspection_record + work_order | 定义设施/巡检/工单、关联键与到期规则，复用查询和证据流程 |

A/B 应能使用同一业务问题与同一框架，得到相同口径的答案。C 使用新的行业定义，不硬套电池 schema。JSON 嵌套或长表整形不能仅凭现有 column 映射宣称已支持，须有明确实现与可追溯预处理。

## 4. 包、模块与分支按需选择

以行业资产积累为目标，推荐让可复用定义、规则、模板与评测回到共享主干。默认不使用“一行业/客户一条长期分支”：分支里的差异难以被新项目发现、组合和独立升级，同一个框架修复也容易被多次复制。包可以暂不拆，但资产必须有清楚的边界、标识、版本和验证记录。

| 方式 | 触发条件 | 维护要求 |
|---|---|---|
| 只新增配置/schema/mapping | 已有适配器、任务与页面足够 | 默认优先；配置有版本，框架源码不变 |
| 新增普通目录/模块 | 存在专属输入整形、算法或页面 | 保留明确入口和依赖注入，不一定增加 package.json |
| 新增 workspace/发布包 | 需要独立复用、发布、依赖隔离或多人维护 | 再提升为独立包，不为目录形式拆包 |
| 短期功能/POC 分支 | 开发、验证假设或隔离实验 | 结束时将通用修复与可复用候选回主干；客户数据/决策留在客户作用域 |
| 长期独立交付线（例外） | 产品行为、合规边界或发布节奏持续分化 | 引用固定版本的公共框架/行业资产，记录升级方式，不靠复制核心维持复用 |

若采用分支，从明确的框架基线开始。公共修复合回主干，再合并/重基到业务线；不能只修一个客户分支就视为框架已修好。Git 分支名不能代替来源、映射、规则和运行清单里的版本。

当前建议先落在同一仓库主干内的资产目录和客户配置引用。只有真实发布/依赖/权限边界需要时才拆包或拆仓库；没有创建具体分支的指令。

## 5. 当前代码的可复用部分和缺口

### 已有基础

- [SemanticMapping](../platform/packages/semantic-engine/src/mapping/types.ts)已区分概念、物理表/视图、字段类型、单位比例、编码映射、时间字段，以及显式 LinkMapping/基数/fanout。
- PostgreSQL/DuckDB 与 StructuredQueryPort、CatalogPort 已分开；同类数据库换 schema，主要应改变登记和映射。
- 行业定义已有对象、属性、关系、身份作用域和规则，客户物理列名不属于行业声明。
- compute 注册、模型端口、RuntimeAdapter、工具传输与证据 envelope 可继续复用。

现有映射主要针对已知 SQL 表/视图，不代表任意多来源连接、嵌套整形和复杂转换均已支持。缺失能力必须明确拒绝或补实现。

### 优先补齐

| 位置 | 要解决的事 | 实施边界 |
|---|---|---|
| 来源与 schema/catalog | 权限、真实类型、schema revision、漂移检查 | 不要求统一所有客户物理表 |
| 客户 mapping | 多种物理结构映射到概念/字段/关系；整形保留 lineage | 简单映射用配置，复杂变换用有界视图/模块 |
| API/Worker | 能源输入、仿真 handler 与通用代码分开；正式 HTTP→controller 接通 | 优先复用注册表和静态注入，不强制插件平台 |
| UI | profile、菜单与专属结果 renderer 由部署/场景提供 | 简单查询复用界面，复杂场景才增加页面 |
| 规则与物化 | 修复例外丢失、跨实体拼接、首批 1,000 条截断 | 不能通过删掉本体或必要解耦来完成验收 |
| 核验与发布 | 正文/时间/证据一致性、模型协议、持久化与恢复 | 场景共享平台完成条件，不能自行放宽 |

只有现有 ProfileSpec、ComponentManifest、OperationRegistry 无法清楚表达真实需求时，才增加 ScenarioManifest/contribution。上一稿的新接口和通用场景 API 不再是首轮硬性前置。

能源合成输入、专属 API 装配、simulation stage、EnergyPlanPanel/客户端 DTO、固定导航与默认 home-energy profile 仍应从通用执行代码中隔离。可先集中到普通场景目录，既有合理分离的行业声明/计算包无需反向合并。服务端依赖不能随场景 UI 进入浏览器。

## 6. 组织方式

在当前 monorepo 内，优先明确四类内容：

- **公共框架**：现有 contracts/core/application/tool-services/semantic-engine/provenance 及通用宿主。
- **配置与声明**：行业 schema、身份与规则；客户 source/mapping；部署的 runtime/model/data/transport 组合。客户配置可只保存受控引用，不提交裸密钥或客户原文。
- **适配器**：来源读取、数据库方言、模型或协议实现。
- **场景模块（按需）**：专属输入、计算装配、模板、页面与独立测试。

这些内容可以是普通文件/目录、既有包里的显式模块或独立包。行业资产从共享主干维护，客户部署引用其明确版本；短期分支沿用相同职责边界，不先建立一套复杂插件安装系统。

## 7. 实施顺序与验收

先准备同一能源业务的两份**结构确实不同**的数据，再准备一个非能源行业的小样例。交通设施巡检可作候选，最终按可用数据决定。先定义问题、预期答案、来源位置和质量反例，再实现接线。

| 阶段 | 工作 | 验收 |
|---|---|---|
| A 正确性与闭环 | 修复 R01—R13，补正式宿主、调度、正文与恢复 | 实际 HTTP 入口获得同一 run 的可读、已核验答案 |
| B 同业务异构结构 | 能源 A/B 两套 schema、mapping、预处理与来源引用 | 同一口径，切换 source/mapping 后核心不改；不要求新包 |
| C 跨行业数据 | 新行业对象/关系/规则与客户结构，按需补场景模块 | 通用 controller/gateway/核验不增加行业分支判断 |
| D 组织形式 | 按真实复用与交付需求决定目录、独立包或分支 | 选择有明确收益，不把打包形式作为产品验收 |
| E 容量与演进 | 分页、schema 漂移、增量、撤回、双时间、恢复 | 不漏派生；旧答案可追到当时 mapping/来源版本 |

必须覆盖：

- **同语义异结构**：改名、拆表/合表、复合键、编码/单位变化不改通用执行代码；超出映射能力时明确拒绝或采用已声明转换。
- **跨行业异语义**：概念/规则变化，工具、预算、核验、证据协议保持稳定；“有本体↔无本体”不足以代替第二行业。
- **身份与关联**：同名不同实体、跨客户同 ID、多对多、未知连接键、重复聚合有独立预期。
- **可选本体**：不启用语义推理时仍能完成已授权的直接查询/RAG，来源与核验要求保留。
- **去能源依赖**：不启用能源模块即可启动通用流程，不能靠根工作区偶然提升依赖而误判。
- **数据演进/容量**：列删除、类型改变、mapping 升级、来源撤回、超过 1,000 条及读取中更新，均检查版本和完整性。
- **分支复用（若采用）**：同一通用修复和回归用例能同步到不同交付线，不能靠各自修改核心接入第二份数据。

成功标准是新客户/新行业的数据被正确接入、查询、推理和追溯，并且改动留在明确的边界内。

## 8. 行业资产具体积累什么

行业资产是可移植、可解释、可验证的一组业务能力，不要求一定是独立代码包。先积累家庭储能这一明确子域，再按实际业务扩展；不能将一个场景的定义直接称为完整“能源行业标准本体”。

| 资产 | 可共享内容 | 应留在客户/部署侧的内容 |
|---|---|---|
| 语义与术语 | 对象、关系、属性、别名、量纲、时间含义、适用范围及来源 | 客户内部字段名、未经确认的同义归并 |
| 身份与数据质量 | 组合键模板、身份作用域、同名消歧原则、质量检查 | 真实实体 ID、客户具体合并/拆分裁决 |
| 规则与计算 | 有适用条件/来源的规则模板、可执行算法、显式例外 | 客户特定阈值、合同政策、设备参数和策略偏好 |
| 接入经验 | 脱离真实客户命名的结构映射模式、单位/编码转换方法、合成样例 | 实际表列绑定、连接、凭据和客户原文 |
| 业务任务 | 代表性问题、指标口径、参数化查询/计划模板、输入输出约束 | 特定项目的一次性问题与现场执行记录 |
| 评测与失败知识 | 已审定的期望结果、未知/冲突/例外/撤回案例、错误原因和溯源预期 | 未经允许共享的客户样本、模型猜测生成且未复核的金标 |
| 场景能力 | 有复用依据的输入模块、结果视图、计算 handler | 与某次演示绑定的临时页面、品牌素材和硬编码数据 |

通用数据库连接、Agent runtime、预算与证据处理沉淀为框架资产；不复制到每个行业目录。行业能力尽量引用同一份定义和实现，避免“家庭储能”“园区储能”各自复制电池、单位和身份规则。

### 8.1 从项目产出提升为共享资产

1. **记录候选**：在解决需求/缺陷时同时记录业务问题、输入形态、适用范围、来源和验证结果；单个 POC 的资产可先保持 preview。
2. **判断归属**：通用问题回框架；可迁移的行业含义/规则回行业；专属任务回场景；真实客户映射、实例和政策留在客户配置。一次性技巧可以保留项目笔记，不必强行抽象。
3. **提取变化点**：将客户专有名词、表列绑定、阈值、时区等移到显式参数或受控扩展；不能用一个万能 JSON 字段掩盖未理解的差异。
4. **建立独立预期**：由业务/领域责任人确认语义与例外，技术维护者确认契约与可追溯性；测试预期不能仅由当前实现或同一个生成模型反向提供。
5. **验证迁移**：在第二种物理结构上运行相同问题与金标。合成结构可以证明映射机制，但不能冒充第二个真实客户验收；来源标准和明确复用需求也可支持提前沉淀，不机械等待第二单。
6. **发布并引用**：记录资产版本、内容摘要、兼容范围、变更说明、验证覆盖与维护负责人；客户 profile 锁定该版本。新项目选择资产并补客户绑定，不复制整个旧项目。
7. **使用后回流**：新反例进入回归集；可泛化修复回共享资产；客户特例仍保留作用域。升级发布新版本，旧 run/证据继续绑定旧版本。

### 8.2 一个能源例子

共享定义可描述电池、SOC、测点、采样时间与有效范围；客户 A 的百分数列、客户 B 的 0–1 比例长表分别通过确认的 mapping 接入。先验证两者 SOC 的实际业务口径相同，再做尺度转换。

“最低保留 20%”若只是某客户的备电偏好，应作为该部署参数，而不能自动上升为行业通用规则。可以共享的是带参数与约束的备电策略模板，以及“参数未知时不做确定承诺”“不能跨电池拼接证据”等检查和反例。

下一家客户应复用语义、策略接口和评测，仅新增身份/来源绑定、结构映射及必要参数。若每次仍需改公共控制器，说明边界或接入能力需要修正，而不是再复制一个行业分支。

### 8.3 资产的最小登记与版本

每份可共享资产至少有：稳定 ID、业务范围/非适用范围、版本和内容摘要、依赖/框架兼容范围、来源及确认状态、维护负责人、测试用例/数据形态及结果、已知限制、变更说明。

继续复用已有 planned/preview/stable/deprecated 词汇；stable 应表示在明确范围内有验证证据，不能只改枚举值就宣称“行业标准”。标准条文、团队归纳、客户约定和实验假设要分别标注。

Git 保存源文件与变更历史，资产发布生成可校验的版本内容，客户 profile/运行清单保存具体引用。框架版本、行业资产版本、客户 mapping 版本分别记录；一个分支名或 Git commit 不能替代全部业务版本。文件清单即可作为第一版资产目录，不需要先建设资产市场。

客户扩展采用显式引用/扩展：新增字段使用明确 namespace；同名不同单位/含义在 preflight 阶段报冲突；业务规则例外显式表达。禁止用“后加载文件覆盖前文件”悄悄改变行业语义。

### 8.4 与现有代码衔接

[IndustryPackExportBundle](../platform/packages/contracts/src/pack-assets.ts)和[导出服务](../platform/packages/application/src/packages/export-service.ts)已覆盖定义、身份策略、来源无关的映射模板、标准来源、测试套件与内容摘要；[升级服务](../platform/packages/application/src/packages/upgrade-service.ts)使用新 profile 版本替换绑定，可作为积累基础。

当前随包 PackTestCase 仅定义 question、expectedCapabilities 和 expectedStatus，验证重点是能力是否可以装配。它还不能表示业务答案、规则例外、推理支撑、不同 schema 等价性等金标。仓库已有业务/语义 fixtures，应补充资产对这些用例和数据的明确引用，而不是重复另造一套样例或宣称当前已完成行业验证。

下一轮可先将现有家庭储能定义、计算模块、两套结构 mapping、代表问题及已发现反例整理为第一份可重放的预览资产。具体文件可以沿用现有目录；是否增加独立包留给实际版本/依赖边界决定。

衡量积累效果：第二份客户数据的接入改动范围、映射耗时、通过的同口径问题、升级后的回归情况、仍需修改核心的次数。资产数量与分支数量不作为主要成功指标。

### 8.5 Palantir 调研后的补充

依据[官方文档调研](research/palantir-industry-assets-2026-09-23.md)，建议进一步明确“共享资产定义/版本”和“客户安装配置”两个生命周期：客户 profile 绑定具体资产与数据映射，分支只表达开发过程。沿用现有类型能表达时，不必为了名称再建一套 Installation 表或插件框架。

数据源字段映射与业务能力接口分开：前者解释如何读数据，后者解释可支持哪些问题/操作及必需条件。客户定制默认走显式扩展；若选择脱离公共版本独立维护，应记录基线、责任与升级方式。以上仍是设计建议，不改变当前实现事实。
