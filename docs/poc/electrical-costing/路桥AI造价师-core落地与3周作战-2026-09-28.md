# 路桥AI造价师 · core 落地对照与 3 周作战拆解

> 日期：2026-09-28
> 项目：路桥AI造价师｜产研立项 · MVP发包（首期：电气桥架造价）
> 底座：`ontology` 主核心产品线 `feat/main-core-product-20260928`
> 目标：把「自然语言/图纸资料 → 提取关键参数 → 调用报价函数 → 结构化报价表 + 解释」做成可复核、可追溯、可演示的 MVP。
> 性质：规划文档，不是立项书或交付承诺。

---

## 一、结论摘要

1. **core 是正确底座**：它已把"本体 + 有限规则(+例外) + 证据 + 硬核验 + 发布 + 版本/撤回"这套**可复核可追溯的机制**做完大半，正好命中造价的核心难点。
2. **core 是"半成品主机"**：状态文档已确认**模块层较完整、集成层局部打通、产品层未闭环**（K01–K09）。其中 5 处直接卡住本项目。
3. **必须新建一个行业层**：`industry-packs/electrical-costing`（本体）+ `extensions/electrical-costing`（报价函数）+ 图纸/资料提取链路。
4. **3 人 3 周可行，但前提是**：W1 就安排一名 owner 回流 core 的集成补丁（K01/K03/K04/K06/K07），否则本体与报价函数没有落地口。
5. **一句话**：core 是发动机，造价行业包是变速箱+车轮，报价函数是油——三者齐了才能跑。

## 三、core 恰好命中造价的核心难点（最强论据）

立项逐字稿强调：造价的灵魂是**大量 smart if-else 条件判断 + 规范合规 + 变更/撤回**。core 的架构正是冲它去的：

| 造价难点 | core 对应能力 | 位置 |
|---|---|---|
| 计价规则的条件判断 | 按实体的有限规则引擎 | `packages/core/src/rule-conclusion.ts` |
| 规范里的"例外情况" | 规则例外四态（条件 AND NOT 例外；缺失/冲突→unknown）| `packages/semantic-engine/src/rules/*` |
| 一个结论多条来源/规则 | OR 支撑聚合 | 规则求值层 |
| 变更/签证/撤回 | 逐条撤回 + 替代支撑保留 + 历史可复读 | 物化/发布层 |
| 金额/数量可追溯 | 逐断言证据绑定 + 硬核验 + 十进制精确比较 | `packages/core/src/decimal.ts`、verification |
| 换材料/规格/标准 | 行业声明 + mapping 分离，换场景不改框架 | `industry-packs` + `composition` |

对比客户既有的 Blueprint OS（CRM/多维 Excel 式操作平台）：**"专业判断可追溯"就是本项目的差异化**，也正是 core 的强项。

## 四、必须新建的三块

### 4.1 电气桥架本体包 `industry-packs/electrical-costing/`
对象（初稿，待专家确认）：
- `CableTray`（桥架直线段）、`Accessory`（配件：弯通/三通/支吊架等）、`Material`（材质/板材）、`Specification`（宽×高×厚/盖板/表面处理）、`ProjectCondition`（环境/敷设方式/工期）、`PricingRule`（计价规则）、`Quote`（报价结果）。

关系：
- `Specification` 约束 `Material`；`ProjectCondition` 筛选 `PricingRule`；`PricingRule` 产出 `Quote` 项；`CableTray`/`Accessory` 引用 `Specification`。

规则（有限子集 + 例外）示例：
- 板材厚度 → 单价系数；盖板是否计价；配件按"件/套"换算；损耗率；单位换算；特殊环境(防腐/防火)加价；某类项目的例外折扣。

### 4.2 报价计算扩展 `packages/extensions/electrical-costing/`
- 把**客户既有计价规则与试算函数**封装成版本化 compute operation（如 `costing.quote`）。
- 确定性计算、输入参数 Schema、结构化报价表、逐项计算依据。
- 复用 `extensions/home-energy` 的注册模式（`compute/handlers.ts` + operationRef）。

### 4.3 图纸/资料提取链路
- **清单/规格文本优先**：复用 core 文档导入 + 抽取（需补 K06 Schema 注入）。
- **DWG/DXF**：按能力分级——L3（GTJ/GCCP 导出明细，最可靠）> L2（DXF 几何）> L1（图层/文字/块参照）；**扫描件/图片不做工程量复核**。
- **不做图像模型微调**；提取结果一律进"候选→人工确认"（core 已有此链路）。

## 六、3 人 3 周作战拆解

> 假设沿用现有 TypeScript 平台；若客户报价函数是 Python，用 HTTP/子进程适配器桥接，不重写核心。

### 分工
| 角色 | 负责 | 主要产出 |
|---|---|---|
| **E1 本体与抽取** | 造价本体 + 资料/图纸提取 | `industry-packs/electrical-costing`、抽取 prompt/schema |
| **E2 报价与工具** | 报价函数封装 + 结构化输出 | `extensions/electrical-costing`、`costing.quote` operation |
| **E3 core 集成与界面** | core 补丁回流 + run 编排 + UI + 验收 | K01/K03/K04/K06/K07 回流、`CostingPanel`、样本比对 harness |

### 时间线
| 周 | E1 | E2 | E3 | 里程碑（退出标准）|
|---|---|---|---|---|
| **W1** | 本体 v0.1（对象/属性/关系/规则语法）；整理客户规范与样本 | 摸清报价/试算函数接口；封装成 operation + 输入 Schema | **优先回流 K06/K07/K03/K04**；跑通"导入→报价"最小链 | **M1（D5）**：一份样例资料 → 结构化报价表（含依据）|
| **W2** | 清单/规格抽取调优；规则/例外/单位 | 报价表结构定型；计算依据；异常/缺参显式报错 | **回流 K01**（应用入口+发布正文）；`CostingPanel`（参数确认/报价表/解释/证据）| **M2（D10）**：端到端闭环 + 可演示交互 |

## 七、验收 harness 设计（对齐 MVP 验收）

| 立项验收 | 落地方式 | 通过标准 |
|---|---|---|
| 与人工造价结果直接比对 | acceptance harness：真实样本 → AI 报价表 vs 人工黄金表，逐项差异 | 约定容差内一致；差异项可解释 |
| 报价过程可复核 | 每个报价项绑定计价规则 + 输入参数 + 工具调用记录 | 抽检 100% 可回溯到规则与参数 |
| 可追溯 | core run + 证据 + 版本化发布，重启后可读 | 每条关键断言有 evidence 指针；同 hash 正文持久 |
| 可演示交互原型 | 浏览器 E2E + 演示脚本 | 正常 HTTP 流程（不 seed、不手动起 Controller）|
| 保留参数/依据/调用记录 | 复用 core `provenance` + compute 操作记录 | 导出可审计的成本构成 |

**证据链要求**（对齐 core 的硬核验）：
- 数值：工程量 × 综合单价 = 合价（精确十进制，容差 <1%）
- 单位/时间/口径随断言绑定
- 图纸线索不得当工程量；缺数量时明确报 gap，不猜

## 八、风险、前置与不做范围

### 前置确认（开工前）
1. **客户报价函数接口**：库/HTTP/脚本？输入输出格式？权限？（E2 头号前置）
2. **黄金样本**：人工确认过的报价结果 + 字段字典 + 例外集。
3. **领域专家**：能否提供资深造价师做规则签核（会议反复强调是成败关键）。
4. **图纸格式**：先确认是 CAD/矢量 PDF 还是扫描件（决定走 L1/L2/L3 还是放弃量算）。
5. **口径对齐**：工程量单位、损耗率、税率、取费标准逐项对齐。

### 风险
- core 集成未闭环（K01 等）→ 必须先回流，否则 3 周被"造主机"吃掉。
- 图纸理解不确定性最大 → MVP 先"清单/规格自动 + 图纸半自动"，不硬承诺全自动识图。
- 真实模型抽取质量未知 → 用高置信字段确定模型、低置信转人工。
- 3 周对赌：做不出即不接（公司付试错成本）。

### 不做范围（首期）
- 不重构客户完整系统；不覆盖全部工程品类；不做真实设备/生产部署。
- 不训练/微调模型；不建 RPA 式固定场景脚本。
- 不把 costing-master 等第三方知识直接当报价依据（仅作参照，须专家校验）。
