# 路桥AI造价师 · 首期电气桥架造价 —— 复用评估与 3 周冲刺拆解

> 基准：现有平台仓库 `D:/work/ontology`（分支 `feat/local-poc-core-20260923`）。
> 目标：把「自然语言/图纸资料 → 提取关键参数 → 调用报价函数 → 结构化报价表 + 解释」做成可复核、可追溯、可演示的 MVP。
> 本文只做规划，不代表已授权开工。

---

## 一、结论先说

**这是一个新领域、但骨架几乎全可复用。** 你现在的平台把「本体 / 智能体 / 工具调用 / 证据 / 核验 / 审计」做成了**行业无关的通用层**，能源场景只是第一个"行业插件"。做成造价，本质是**照着 `home-energy` 复制一个造价插件**，外加两块真正的新活：**图纸/资料参数提取** 和 **报价函数封装**。

| 层次 | 能源场景现状 | 造价师要做的 |
|---|---|---|
| 通用核心（run/预算/工具/证据/核验/发布） | 已实现 | **直接复用** |
| 行业插件（本体声明 + 领域计算 + UI 面板） | `home-energy` + `extensions/home-energy` | **照抄一份 `electrical-costing`** |
| 关键参数提取 | 文档 span 检索 | 🔶 **新增**（清单/规格文本、图纸） |
| 报价函数调用 | 能源仿真器（确定性计算） | 🔶 **封装客户的报价/试算函数** |
| 真实样本比对验收 | 合成数据 | 🔶 **新增**（接真实样本） |

## 二、可直接复用清单（省掉一大半工作量）

| 仓库模块 | 造价项目里的用途 |
|---|---|
| `packages/core` + `packages/application` | run 工作流、共享预算、阶段编排、取消、幂等、发布 |
| `packages/contracts` | 公共契约：`compute`、`operations`、`document-parse`、`extraction`、`semantic-definitions/publication`、`verification`、`provenance-read`、`rule-extraction` |
| `packages/semantic-engine` | 本体定义、Schema 词汇、实体/关系抽取、身份召回、人工审核、版本化发布 |
| `packages/tool-services` | `data_query` / `document_search` 等工具实现 |
| `packages/adapters` | DuckDB / PostgreSQL / 文档解析 / 不可变 blob |
| `packages/provenance` | 证据归档与只读回溯 |
| `apps/api` | HTTP 路由与 `{data,meta}`/`{error,traceId}` 约定、operator API |
| `apps/web` | Clarity 工作台与"能源面板"的写法（改成"造价面板"即可） |
| `apps/worker` | 有界后台任务 |
| `tests/*`（unit/integration/e2e + 临时 PG 容器 + Chromium） | **整套验收骨架直接搬** |

一句话：**你需要的"可信闭环机制"已经写好了，造价项目只是换一个"行业插件"和几处输入输出。**

## 三、必须新建的部分（这才是 3 周的活）

### 1. 电气桥架造价本体（新行业包）
- 目录：`industry-packs/electrical-costing/`
- 对象：`Material`（材料）、`Specification`（规格）、`ProjectCondition`（工程条件）、`PricingRule`（计价规则）、`Quote`（报价结果）。
- 关系：规格约束材料、工程条件筛选计价规则、计价规则产出报价项。
- 单位/身份范围/规则模板，照 `home-energy` 的结构声明。

### 2. 报价计算扩展（新 extension）
- 目录：`packages/extensions/electrical-costing/`
- 把**客户既有计价规则与试算函数**封装成版本化 compute operation，例如 `costing.quote`。
- 确定性计算、输入参数 Schema、结构化报价表、每项的计算依据。

### 3. 关键参数提取（最大不确定性）
- **先做**：清单/规格/规范文本 + 结构化表格（工程量、规格、材质、数量）。
- **再做**（可降级）：图纸参数提取。MVP **不硬承诺全自动识图**；先做"多模态抽取 + 人工确认"，图纸仅预留接口（对应你仓库"能力需契约确认"的边界）。

### 4. 造价 UI 面板
- 照 `EnergyPlanPanel` 改一个 `CostingPanel`：参数确认区、报价表、解释区、工具调用/证据记录。

### 5. 真实样本验收
- 接客户人工造价结果样本，做"AI 报价 vs 人工报价"比对。

## 四、3 周冲刺拆解（3 名工程师）

> 假设沿用现有 TypeScript 平台（若客户报价函数是 Python，则 W2 用"HTTP/子进程适配器"桥接，不重写核心）。

### 分工
| 角色 | 负责 | 主要产出 |
|---|---|---|
| **E1 本体与抽取** | 造价本体 + 资料/参数提取 | `industry-packs/electrical-costing`、提取 pipeline |
| **E2 计算与工具** | 报价函数封装 + 结构化输出 | `extensions/electrical-costing`、`costing.quote` operation |
| **E3 闭环与界面** | run 编排 + UI + 证据 + 验收 | `CostingPanel`、端到端 E2E、样本比对 |

### 时间线
| 周 | E1 | E2 | E3 | 里程碑 |
|---|---|---|---|---|
| **W1** | 本体 v0.1（对象/关系/规则）；整理客户规范与样本 | 摸清客户报价/试算函数接口；封装成 operation + 输入 Schema | 跑通"提取→报价→输出"最小链路；搭造价面板骨架 | **M1（D5）**：能对一份样例资料产出结构化报价表 |
| **W2** | 文本/清单抽取调优；规则抽取与审核发布 | 报价表结构定型；计算依据；异常/缺参显式报错 | 闭环编排 + 面板（参数确认、报价表、解释）；证据/工具记录 | **M2（D10）**：端到端闭环 + 可演示交互 |
| **W3** | 规则/规格覆盖补全；样本回归 | 与人工结果口径对齐（单位/损耗/税率） | 真实样本比对、解释完善、演示脚本、浏览器 E2E | **M3（D15）**：真实样本可比对、过程可追溯、原型可演示 |

### 依赖关系（谁卡谁）
```
E1 本体/抽取 ─┐
              ├─→ E3 闭环/UI ─→ 真实样本比对
E2 报价函数 ──┘
（E1、E2 并行；E3 依赖两者产出接口，W1 内先定接口契约）
```

## 五、验收怎么测（对应立项的 MVP 验收）

| 立项要求 | 怎么落地验证 |
|---|---|
| 与人工造价结果直接比对 | acceptance harness：真实样本 → AI 报价表 vs 人工报价表，逐项差异 |
| 报价过程可复核 | 每个报价项绑定定价规则 + 输入参数 + 工具调用记录（证据链） |
| 可追溯 | 用平台的 run + 证据 + 版本化发布，重启后仍可回溯 |
| 可演示交互原型 | 浏览器 E2E + 演示脚本（照现有 `test:e2e` 模式） |
| 保留关键参数/依据/调用记录 | 复用 `provenance` + `compute` 的操作记录 |

## 六、前置条件与风险（开工前必须确认）

1. **客户报价函数接口**：是库、HTTP 还是脚本？输入/输出格式？权限？——这是 E2 的头号前置。
2. **图纸可行性**：先和客户确认"图纸要自动提取到什么程度"。若太贵，MVP 降级为"文本/清单自动 + 图纸辅助录入"。
3. **口径对齐**：工程量单位、损耗率、税率、取费标准必须和造价员逐项对齐，否则"比对"没意义。
4. **规则显性化**：很多计价经验在老师傅脑子里；本体先收录**显性规则**，隐性经验后续迭代。
5. **DataOS/AgentOS**：立项书若把它们写成"复用已有能力"，注意你仓库的规范是 `未验证能力不得成为实现前提`——先核实再依赖。

## 七、与你现有仓库的"最小改动"清单

新增（不改通用核心）：
```
industry-packs/electrical-costing/        # 造价本体声明
packages/extensions/electrical-costing/   # 报价计算 operation
apps/web 的 CostingPanel + 路由贡献        # 造价界面
apps/api 的造价装配入口                     # 复用 run/operator 路由模式
tests 的造价 acceptance 样例                # 真实样本比对
```
**原则不变**：通用 App/API/Controller/Gateway 不出现"桥架/造价"字样；造价全部留在插件与部署装配里（`tests/architecture` 的边界检查会自动守护）。
