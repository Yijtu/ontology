# 家庭能源智能调度 Agent —— 功能总览（2026-09-26）

> 本文写给"想快速看懂现在到底有什么"的人。不假设你读过 PRD/SPEC，也尽量不用术语；术语集中在文末[名词小抄](#六名词小抄)。

---

## 一句话看懂

这是一个**家庭能源管家**：你告诉它"明天怎么充放电"，它会结合天气、电价、家庭用电和你的备电要求，算出一份 **96 个 15 分钟时段**的充放电计划，能模拟执行、能解释"为什么这么排"，而且**每个数字都能自证来源**——查不到出处的数字它宁愿不显示。

它目前跑在你自己电脑上（本地演示），数据是**合成的**，不接真实设备。

## 二、页面怎么逛

打开 `http://127.0.0.1:5173/` 后，**左侧边栏**有 6 个入口：

| 入口 | 干什么 |
|---|---|
| 配置工作台 | 给开发/交付人员用：选行业、跑预检、激活配置 |
| 业务问答 | 用普通语言问问题（比如"某站点 SOC 均值是多少"） |
| 导入任务 | 看文档导入/抽取的处理进度 |
| 候选审核 | 人工确认"这个实体/关系对不对"后再发布 |
| 证据与历史 | 回溯某个结论的原始证据和历史版本 |
| **家庭能源计划** | 本文重点，见下 |

**家庭能源计划页**从上到下依次是：

```
┌─ 顶部指标行 ──────── 电池SOC / 备电下限 / 本体关系数 / 计划净成本
├─ 家庭能源总览 ────── 能源流图（光伏→家庭/电池，电网→家庭）+ 96时隙滑杆 + 四张数据卡
├─ 为什么这样安排 ──── 用人话说明排布逻辑 + 三条保证
├─ 场景卡 A/B/C/D ──── 一键切换 4 个验证场景
├─ 情景输入 ────────── 手动调 ReserveSOC / 天气 / 备电窗口 / 预测故障
├─ 已保存计划版本 ──── 历史版本及状态
├─ 本体解释与运行证据 ─ A4：三跳关系链（见下）
├─ 计划版本（新→旧）── 每个候选策略的费用/期末电量/备电是否满足
└─ 模拟执行 ────────── 执行按钮 + 96 条执行回执
```

## 三、能做什么（按"你会怎么用"来讲）

### 1. 生成一份储能计划
- **操作**：点"构建情景"→"生成计划"。
- **你会看到**：三种策略（`self_consumption` 自用优先、`reserve_first` 备电优先、`price_window` 电价窗口）的费用、期末电量、备电是否满足；被选中的那份标记为 **Selected**。
- **边界**：只在"已测试的有限策略"里选，**不承诺全局最优**。

### 2. 改条件，看"新计划 vs 旧计划"
- **操作**：改天气或 ReserveSOC，再生成一次。
- **你会看到**：新版本变 Selected，**旧版本自动标 Superseded**；并给出差异——PV 预测变了多少、成本差了多少、哪些时隙受影响、原因是什么。
- **边界**：只有"同天气、同电价、同初态"才能比较成本；口径不同会**拒绝**给出节省结论。

### 3. 模拟执行
- **操作**：对当前 Selected 计划点"请求模拟执行"。
- **你会看到**：96 条回执，每条经历 `Requested → Accepted → Observed`，并显示电池前后 SOC；执行结果**重启服务后仍读得到**；同一计划重复点不会重复执行。
- **边界**：永远是 `simulation`（模拟），**`live`（真机）一律拒绝**，不发送任何设备指令。

### 4. 问"为什么这么排"（本体解释，代号 A4）
- **操作**：生成计划后，看"本体解释与本次运行证据"区块。
- **你会看到**：当关系链被人工确认并发布后，显示一条**三跳因果链**：
  `天气 → 光伏预测 → 能源计划 → 设备`，
  并且每一步都绑定**本次运行**的真实数据编号（不是静态示意图）。
- **边界**：关系没确认、被撤回、或换一个租户来读，都只会显示 `limited` + 缺口说明，**绝不编造因果**。

### 5. 制造异常，看它"停得住"（异常处理，代号 D1）
- **操作**：把"预测数据"选成"有效期不足"或"下午预测缺失"，再生成计划。
- **你会看到**：状态变 `insufficient_data`（数据不足），**没有** Selected 版本，执行按钮**变灰**，并提示原因和恢复建议。
- **边界**：绝不"硬编一个计划"或产生"执行成功"的假回执。

### 6. 其他行业场景（同一套框架）
- **SOC 查询**：同一个问题分别用"A：宽表"和"B：长表"两种数据库结构，结果都应是 45%，验证"换数据结构不改核心"。
- **交通巡检**：问"north 区有哪些设施待巡检"。
- **文档溯源**：问"已导入文件里的巡检频率原文"，返回**原文引句 + 位置**。
- **operator 只读 SQL**：配置后，用真实只读数据库视图替换合成表。

## 四、四个演示场景（能源页的场景卡）

| 卡片 | 一句话 | 点它会发生什么 |
|---|---|---|
| **A 正常一天** | 上午阴、下午晴；备电保底 20% | 生成基准计划 |
| **B 天气变化** | 下午转阴雨 | 上午光伏不变、下午下调 → 新计划，旧计划 Superseded |
| **C 提高备电** | 备电从 20% → 60%，且 17:00 起生效 | 当前 SOC 仍是 35%，计划要先补电再检查晚间是否达标 |
| **D 预测过期** | 预测数据失效/缺失 | 计划停下，`insufficient_data`，不可执行 |

## 五、支撑它的"看不见的能力"

这些是你不会直接点，但让一切可信的机制：

1. **同一条 run（可审计流水线）**：每个问题从"问"到"答"是一条记录，中间每一步（取数、计算、核验、发布）都可回溯。
2. **证据绑定 + 硬核验**：数字、单位、来源必须自洽；对不上就不发布（宁缺毋滥）。
3. **算法与场景分离**：换一份客户数据结构，原则上只改"来源配置/映射"，不动通用核心。
4. **本体是可选增强**：简单问题直接查数据；复杂问题才用语义关系解释。

## 六、名词小抄

| 术语 | 大白话 |
|---|---|
| **run** | 一次"问-答"的完整可审计记录 |
| **证据 / artifact** | 每个数字背后的原始数据指针，不可篡改 |
| **硬核验** | 发布前自动检查数字/单位/来源是否自洽，不通过不发布 |
| **本体 / 实例关系** | 对象之间的语义关系（天气→光伏→计划→设备），**必须人工确认+发布**才作数 |
| **三跳** | 上面那条链的四个节点、三段关系 |
| **Selected / Superseded** | 当前生效版本 / 被取代的旧版本 |
| **simulation / forecast / observed / synthetic** | 数据标记：模拟 / 预测 / 实测 / 合成 |
| **ReserveSOC** | 你要保留的备用电池下限（%） |
| **96 时隙** | 一整天切成 96 段（每段 15 分钟）逐一安排 |

## 七、有意的"不能做"清单

**不是没做，是明确边界**（避免误解为能力缺失）：

- ❌ 不接真实设备、不发真实控制指令（恒为模拟）。
- ❌ 不承诺省钱最优、不代表真实账单。
- ❌ 不猜答案：数据不足就明确报缺口，不兜底编造。
- ❌ 不自动信任模型：模型只能提"候选"，人工审核发布后才生效。
- ⚠️ 尚未交付：任意客户表自动识别、JEV 概率决策、多副本部署、公司模型真实网关。
